# 架构

> 内核的工作是**正确**：一个会话的状态从不倒退，一个预算从不被超支，一条事件从不丢失。
> 一切关于**策略**的东西——用哪个模型、哪些工具、谁能调什么、花多少钱——都是注入的。

这份文档讲系统的形状：有哪些部分、每一部分承诺什么、一轮请求怎么穿过它们。

---

## 1. 两条承诺

| 承诺                       | 含义                                           | 后果                                                           |
| -------------------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| **机制在内核，策略在外部** | 内核保证不变量，它从不决定什么被允许           | 一个内核服务不同规则的部署，不需要分叉                         |
| **对话归调用方**           | 内核记录它实际发出的；它不保存对话的第二份副本 | 没有第二个真相可分歧，于是没有游标、没有历史合并、没有压缩动作 |

第二条是这套设计的支点，§6 专门讲它。

---

## 2. 它不是什么

不是 agent 框架：循环是调用方的。不是模型网关：没有"不依赖会话地调模型"的端点，
因为预算要在花费前强制，而那需要一个会话。不是 RAG 管线：检索是一个工具。
不是集群编排器：它说一个会话属于谁，它不做调度。不是沙箱：它调用一个隔离后端，
并记录它**强制**了什么。

---

## 3. 四条不变量

每一条都由一个类型或一个唯一入口承载。如果它是约定，它就只是一个建议。

|        | 不变量                         | 由谁强制                                      | 为什么不可谈判                             |
| ------ | ------------------------------ | --------------------------------------------- | ------------------------------------------ |
| **I1** | 一个会话一个写者               | 宿主持有的租约；`&mut` 在整个系统里只出现一次 | 日志的稠密有序序列是重放、游标与审计的基础 |
| **I2** | 每一次状态变更是一条不可变事实 | 唯一追加路径；事实只在内核内构造              | 重放得到一个状态，而不是一个故事           |
| **I3** | 预算在花费之前检查             | 任何模型/工具调用之前先拿到许可               | 花完再查是账单                             |
| **I4** | 内核记录**它自己**产生的       | 事实构造器私有                                | 否则记录就是调用方的声称                   |

三条后果值得说清，因为它们最容易做错：

- **失败的尝试仍然付钱。** 一条流出过内容然后断掉的流花了钱，账本要记它。
  未上报的计数器保持"未上报"，而不是被当成零悄悄加进去。
- **"开始了但没有结局"的副作用不被猜。** 重试会重复它，跳过会丢掉它。
  会话携带着这份不确定，并拒绝开始下一轮，直到调用方明确承认。
- **内核不拒绝它无法判断的事。** 一条它从未派发过的工具结果会被记成"未验证"，
  而不是被拒绝：拒绝只会把同样的工作推进 `instructions` 里的自然语言，那里什么都看不见。

## 4. 分层

```text
contract   纯类型                                       零 I/O、零 async、零运行时
   ▲
 ports     宿主必须实现的 seam                          没有实现
   ▲
 kernel    状态机、日志、门禁、轮次                      只认识 ports
   ▲
 wire      信封、路由、错误映射、帧                      只认识 contract
   ▲
 宿主      库形态（embed）· 服务形态（daemon）· CLI
```

这张图是单向的，而且是**被检查**的，不是被记住的：`wire` 不许命名 `kernel`，
`kernel` 不许命名 `wire`，两者都不许命名一个传输。一个结构性测试读 manifest，
而不是相信 review。

`contract` 里没有 trait、没有 async——因为 trait 需要一个运行时，而运行时是宿主做的决定。
这也是为什么 ABI 文档能从它生成：一个 SDK 生成器只读一个 JSON 文件，永远不编译 Rust。

---

## 5. 六个 seam

第六个之外再加一个需要论证：每一个都是"宿主必须实现的一件事"，而一个必须实现七件事的宿主，
通常第七件实现得很糟。

| seam          | 回答什么                   | 形状                                   |
| ------------- | -------------------------- | -------------------------------------- |
| **Generator** | 怎么把请求变成答案         | 一次调用，或一条事件流                 |
| **Embedder**  | 怎么把文档变成向量         | 一批进，向量按序出                     |
| **Decider**   | 怎么回答一批类型化问题     | 问题进，答案与拒答出                   |
| **Tool**      | 怎么跑一次调用             | `execute(binding, args)`；失败变成内容 |
| **Runner**    | 怎么启动并管理一个进程会话 | **会话**，按游标读——不是一次性调用     |
| **Clock**     | 测试里现在是什么时间       | 一个方法背后的确定性时钟               |

两处形状是刻意的：

- **一个供应商是一个结构，不是每个能力一个接口。** `Provider` 持有一个必需的
  generator 和可选的 embedder / decider / catalog；缺席的 seam 是 `None`，而不是一个
  永远回"不支持"的 stub。它的字段是私有的、经 builder 装配，所以"没有 generator 的
  供应商"不是一个校验失败的值——它是一个**写不出来**的值。
- **一个工具通过两个方法看会话。** 一个 id、一个自己的抽屉，加上它**声明过**的能力。
  没声明的能力读出来是缺省的——这就是"工具拿不到它没要求过的权限"在不拷贝、不置空的前提下
  被强制的方式。

## 6. 对话归调用方

常见的形状是相反的：内核保存消息列表，调用方发增量。那个形状换来服务端组装提示词，
而它要付一整套机器——历史游标、合并规则、压缩动作、"这一轮提交不提交"的开关、
以及一条用来发现"调用方和服务端对历史的理解不一致"的摘要链。

这里调用方发**整段 `messages`**，逐字节，内核：

1. 检查它良构（每个工具调用都有结果、每个名字都可调用）；
2. 检查模型接得住（输入种类、输出模态、上限）；
3. 记一条 `PromptSent { messages, digest, count, bytes }`——内容寻址，所以同一条消息
   在十轮里出现只存一份；
4. 原样转发，只加上内核拥有的部分：工具集，以及那段 preamble（技能摘要，每个一行）。

**它删掉了什么**：历史游标、合并规则、压缩动作、提交开关、摘要链、被压掉的 blob 的钉住。
**它当作问题删掉了什么**：分歧。只有一个副本时，两份不可能不一致。

**它的代价，说清楚**：

- 服务端不能替你组装上下文——技能段由内核渲染，其余归你；
- 一段导入的对话，如果用了这个部署没有的工具，会被拒绝，因为模型不能调用它没被展示过的工具；
- 压缩是你对自己数组的编辑。它仍然是**可见的**——下一条 `PromptSent` 的 `count` 与
  `digest` 不同——它只是不再是内核执行的一个动作。

## 7. 一轮的完整路径

```text
调用方                     内核                            适配器
  │                          │
  ├─ POST /inference ───────▶│
  │                          ├─ 租约：一个会话同时一轮（423 + Retry-After）
  │                          ├─ 授权：confine、tools、models
  │                          ├─ 能力：模态、输入种类、上限
  │                          ├─ 预算：花费之前预留
  │                          ├─ 暴露：提示词里带哪些工具
  │                          ├─ append TurnStarted            ← 提交点
  │                          ├─ append PromptSent
  │                          ├─ 路由：走链 ─────────────────▶│ generate_stream
  │                          │◀─ 事件 ────────────────────────┤
  │                          ├─ 折叠：文本、工具调用、用量
  │                          ├─ 结算：账本、用量、停止原因
  │                          ├─ append MessageCompleted | TurnFailed | AttemptFailed
  │◀─ message + outcome ─────┤
  │   + warnings + seq       │
```

**提交点是 `TurnStarted`。** 在它之前，一次失败不花钱，是一个状态码。在它之后，日志是记录，
调用方从事实里得知结局。一个没有留下任何记录的轮次，不能看起来像"还在跑"——这就是为什么
三种结尾是穷尽的。

工具调用不在这里执行。内核记录"模型要了它"，结束这一轮，调用方在第二个请求里派发——
所以工具可以失败、可以等人、可以并发扇出，而同时那一轮早就结束、早就记了账。

---

## 8. 并发

一个会话**同时只跑一轮**。第二个并发调用得到 `423 Locked` 和 `Retry-After`；
`cancel` 立即生效，而 `narrow` 与 `close` 要等。

没有 `ETag`、没有 `If-Match`、没有 `412`。那个头回答的是"服务端的历史还在吗"，
而服务端没有历史。剩下要防的只是"两个轮次都花钱"——一把锁，不是比较交换。

重发一次 `inference` 就是第二轮，它会再花一次钱。"上一次成没成"的答案是**读日志**，
看那个 `step` 有没有 `message_completed`，而不是一张按幂等键存、还要跟着保留策略老化的表。

---

## 9. 隔离

四个**正交**维度，不是一个梯子：文件（读根、写根、只读）、网络（default / proxy /
allow-list / deny-all，带规则与 TLS 拦截）、环境（白名单 + 注入值）、资源（cpu、内存、
磁盘、输出）。一个有序枚举在表格里好看，但它表达不了"`/srv` 下可写、不许联网、
只看得见这四个环境变量"。

一个后端**声明**它能强制什么，而它强制不了的策略**在构造期就被拒绝**，而不是运行期降级。
后端还要区分"边界拒绝"和"执行失败"——前者意味着**什么都没跑**，这正是"先试一条命令、
只在边界说不之后才问人"能够成立的前提。

## 10. 记录

```text
facts      (session, seq) → at, kind, body      只追加、稠密、有序
checkpoints session       → version, seq, state  日志的缓存
blobs      id = hash      → content             内容寻址、去重
```

日志是真相，checkpoint 是它的缓存。恢复是 `load(checkpoint)` 然后折叠尾部；
存储拒绝一个不比已有版本更新的 checkpoint，这就是陈旧句柄被发现的机制。

每一条事实同时也是 ABI：一帧流**就是**一条事实，所以词汇是故意封闭的，
而遇到未知 kind 的客户端应当忽略它，而不是失败。

可观测有两根轴，因为一根答不了另一根的问题：

|          | 载体                         | 回答                   |
| -------- | ---------------------------- | ---------------------- |
| **纵向** | 事实日志                     | 这个会话为什么变成这样 |
| **横向** | trace 上下文（作为参数传递） | 时间花在哪些服务上     |

## 12. 被否决的设计

记下来，因为它们会以更好的包装回来。

| 被否决的                      | 它能换来什么                           | 为什么不要                                               |
| ----------------------------- | -------------------------------------- | -------------------------------------------------------- |
| 内核持有对话                  | 服务端组装提示词、多个客户端看到同一份 | 它造出第二个副本，而调和两个副本的机器比这个功能本身更大 |
| 无状态的模型调用端点          | 路由、重试、记账集中一处               | 一旦它存在，"为什么不能内嵌"就永远只能回答"还没"         |
| 内核拥有压缩                  | 调用方不用考虑窗口                     | 那是在编辑它不拥有的数据，而且必须押注几十种策略之一     |
| 调用方自选沙箱策略            | 请求更简单                             | 能自己命名策略的调用方，能命名最不严的那一个             |
| 用 `ETag` / `If-Match` 管轮次 | 乐观并发                               | 它回答一个已不存在的问题；真正的需求是一把锁             |
| `record_event` syscall        | driver 不用自己造事实                  | 它唯一的实际用途是伪造内核必须当真的事实                 |

## 13. 细节在哪

在代码里，一个 crate 一份。每个 crate 开头都有一段文档，说明它拥有什么、它拒绝什么、
它守着哪条不变量、它邀请哪些错误——`contract` 解释它为什么没有 trait 也没有 async，
`ports` 解释为什么缺席的 seam 是 `None` 而不是一个 stub。

一个 crate 文档的形状，和这份文档的形状一样，只是低一层：先说不变量，再说承载它的类型，
最后说"选了这个设计而不是那个"的代价。
